# STM32 工程识别与资料管理

本 Skill 的首要任务是在修改代码或讨论外设实现之前，准确理解当前工程。它以证据为依据，不根据目录名、芯片系列简称或过往项目经验猜测完整型号和硬件配置。

按任务需要加载 `references/` 中的资料，不把所有章节当作每次都要执行的清单。

## 适用任务

- 阅读一个现有 STM32 工程并梳理目录、源文件和模块关系。
- 识别工程实际面向的 MCU 完整型号、封装和项目构建目标。
- 核对 `.ioc`、CubeMX 生成代码、编译配置和链接脚本是否一致。
- 识别工程使用的 IDE、编译器、STM32Cube 固件包和 HAL 版本。
- 查找并整理对应 MCU 的 Datasheet、Reference Manual、Errata Sheet、Programming Manual、Application Note 和 HAL 文档。
- 将 MCU、外设、引脚、时钟、DMA、中断与原理图/PCB资料建立可追溯关系。
- 为后续固件开发生成可靠的工程信息基线。

## 不负责的任务

- 不编写具体控制算法、外设驱动或应用代码；转交 `stm32-firmware`。
- 不负责详细的 TIM/PWM、ADC/DMA、通信外设参数和触发时序审核；转交 `stm32-peripheral`。
- 不替用户修改 `.ioc`、重新生成 CubeMX 代码、修改 IDE 工程配置或改变链接脚本。
- 不负责安装 IDE、编译器、CubeMX、驱动或配置开发环境。
- 不负责构建、烧录、在线调试和硬件功能测试。
- 不根据 MCU 数据手册单独推断整块 PCB 的电路连接或外部器件参数。

## 与其他 Skill 的分工

- 当前任务主要是“先弄清工程是什么、芯片是什么、资料在哪里”：使用本 Skill。
- 需要进一步判断外设配置、时钟、触发、同步或板级信号链：使用 `stm32-peripheral`。
- 需要编写或修改 C 源码、HAL 调用、中断回调或 DMA 数据处理：使用 `stm32-firmware`。
- 简单代码任务不必为了形式完整而依次调用全部 Skill；只有遇到相应问题时再切换。

## 核心工作流程

1. **确定工程根目录。** 查找项目级 `AGENTS.md`、README 和工程入口文件。若工作区存在多个候选工程，先判断当前任务对应哪一个；无法判断时询问用户，不擅自选取。
2. **建立工程清单。** 识别 `.ioc`、IDE 工程文件、构建文件、启动文件、设备头文件、链接脚本、HAL/CMSIS 目录、用户源代码和硬件资料。按 [工程识别](references/project-discovery.md) 执行。
3. **交叉核对 MCU 身份。** 分别记录“工程构建目标”和“实际硬件芯片”。检查完整型号、封装、设备宏、启动文件、链接脚本和硬件 BOM/丝印。按 [MCU 型号识别](references/mcu-identification.md) 执行。
4. **核对配置与构建元数据。** 对照 `.ioc`、生成初始化代码、实际参与构建的源文件、编译宏和链接配置。识别 IDE/工具链及版本，但不启动构建。按 [配置与工具链识别](references/ioc-and-toolchain.md) 执行。
5. **建立硬件上下文。** 将 MCU 引脚、外设实例、时钟、DMA、中断与原理图、PCB、BOM 对照。按 [硬件资料关联](references/hardware-context.md) 执行。
6. **查找官方芯片资料。** 以完整型号进入 ST 官方产品/文档页面，核对文档适用范围、文档编号、版本和硅修订版限制。按 [官方资料查找与管理](references/documentation-management.md) 执行。
7. **形成工程基线。** 使用 [工程识别报告模板](references/project-inventory-template.md) 输出已确认信息、证据位置、冲突和未知项。没有证据的内容明确标记为“未知”或“待核实”。

## 证据与结论规则

- 将“工程配置意图”“实际参与编译的固件配置”和“实物硬件”分开记录，不能把三者混为一谈。
- 每个关键结论尽量附文件路径、配置项、源代码位置或官方文档编号。
- `.ioc` 反映 CubeMX 项目配置，但不能单独证明当前 C 源代码没有被手工修改，也不能证明某个源文件实际参与了构建。
- 启动文件、设备宏、设备头文件、链接脚本和工程构建配置应相互印证。若冲突，先报告冲突。
- 原理图/BOM 说明设计意图；若要确认实际焊接的芯片，应结合实物丝印、装配记录或用户确认。
- 不把系列级资料误当成某个完整订货型号的全部规格。封装、容量、引脚复用和硅版本必须按具体型号核对。
- 官方页面显示的最新文档不一定就是当前工程所使用的软件包版本；两者应分别记录。
- 对推断、未知和冲突进行显式标记，不用肯定语气掩盖证据不足。

## 关键边界

- 默认只读分析。未经用户明确授权，不修改 `.ioc`、IDE 工程文件、编译宏、链接脚本、启动文件、时钟配置、引脚配置或 CubeMX 生成代码。
- 不覆盖、移动或删除用户文件；不自动重命名现有工程目录。
- 不将旧工程强行改造成某个统一目录结构。先描述现状，再提出建议。
- 不因找到某个外设名称就认定它已配置、已启动或已连接到板上。
- 不因 MCU 数据手册列出某项功能就认定当前封装、引脚或板级电路可用。
- 不读取或输出与工程识别无关的密钥、令牌、密码和 `.env` 等敏感配置内容。
- 对电力电子控制板，识别 PWM、ADC、比较器、门极驱动使能和故障信号时，尤其要区分 MCU 软件配置与真实硬件保护链路；不擅自建议解除保护或使能功率级。

## 完成标准

- 工程根目录和实际使用的工程入口已识别。
- 工程目标 MCU 与实物芯片身份分开记录，型号和封装有证据支持。
- `.ioc`、源码、构建配置、启动文件和链接脚本之间的差异已说明。
- IDE/编译器/HAL 版本只在证据支持时填写。
- 关键外设和引脚配置能追溯到工程文件、官方资料或硬件图纸。
- 对应的 ST 官方文档已定位，适用型号和版本已核对；缺失资料明确列出。
- 报告区分已确认、推断、未知和冲突，不包含未经验证的硬件结论。
