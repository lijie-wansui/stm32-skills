# MCU 完整型号与工程目标核对

## 1. 必须分开记录的两个对象

### 工程构建目标
当前源代码和构建配置准备生成给哪一个 MCU 运行的固件。

### 实际硬件芯片
目标板上实际焊接的 MCU 是哪一个完整型号和封装。

两者可能不一致，例如工程从旧芯片迁移、替换过 MCU、复制了其他项目配置，或实物 BOM 与设计文件不同。不要用其中一个替代另一个。

## 2. 完整型号的重要性

STM32 系列简称不足以确定具体资源。完整订货型号通常包含产品系列、功能/容量等级、引脚封装、温度等级等信息；不同产品线的编码规则并不完全相同。

必须按 ST 对应产品线的订货信息解释型号，不要用一个系列的后缀规则套用另一个系列。

可能影响工程判断的差异包括：
- Flash 容量和 SRAM 容量。
- 封装及实际引出引脚。
- 可用外设实例和通道。
- GPIO 复用功能与引脚电气特性。
- 温度等级、供货和产品版本。
- 芯片硅修订版及适用勘误。

## 3. 工程目标的交叉证据

检查并交叉核对：

1. `.ioc` 中选择的 MCU/封装信息（若项目有 `.ioc`）。
2. IDE 或构建系统中的设备宏，例如 `STM32...` 系列宏；具体宏名以工程为准。
3. 编译器包含的设备头文件。
4. 启动文件的设备系列/型号标识和向量表。
5. CMSIS Device 目录和 HAL 包的目标系列。
6. 链接脚本中的 Flash/RAM 起始地址与长度。
7. 工程说明、硬件 BOM 和原理图中的 MCU 料号。

不能把某一项当作唯一证据。尤其是 `.ioc`、README 和目录名可能过时；链接脚本也可能为 Bootloader、双镜像、保留区或自定义内存布局而缩小可用区域。

## 4. 实物芯片识别

如果任务涉及实物板：
- 优先查看芯片表面丝印、装配 BOM、采购料号和板卡版本。
- 必要时查看高清芯片照片；丝印不完整时，明确说明无法仅凭照片确认完整订货型号。
- BOM 表示设计/装配意图，不一定证明返修后实物没有被替换。
- 原理图和 PCB 说明板级设计连接，不等于芯片实际焊接状态。
- 如果没有实物证据，报告“实物芯片型号未确认”，不要把工程目标写成实物确认结果。

## 5. 资源信息的核对

完成型号确认后，再从对应官方 Datasheet 核对：
- 核心类型和主频能力。
- Flash/SRAM 容量。
- 封装、引脚数和 pinout。
- 外设实例及通道资源。
- GPIO 电气特性、绝对最大额定值和工作条件。
- 订货信息和温度等级。

从对应 Reference Manual 核对：
- 外设工作机制。
- 时钟、复位、寄存器、触发源和中断。
- DMA 请求/通道或 Stream 映射（按具体系列架构）。
- 定时器、ADC、通信接口等模块细节。

从对应 Errata Sheet 核对：
- 适用芯片型号范围。
- 硅修订版适用范围。
- 外设限制、规避措施和软件影响。

不要根据“某系列通常有某外设”推断某个具体型号或封装一定具有该资源。

## 6. 发生冲突时

若 `.ioc`、编译宏、启动文件、设备头文件、链接脚本或 BOM 指向不同芯片：

1. 暂停基于该芯片的外设 API、引脚或内存结论。
2. 列出每个证据指向的型号及文件位置。
3. 区分是配置遗留、迁移不完整、文件误放还是硬件型号不确定。
4. 询问用户当前目标板和实际 MCU 料号。
5. 在冲突消除前，不修改设备宏、启动文件、链接脚本或工程配置。

## 7. 报告用语

使用明确状态：
- **已确认：** 多项一致证据支持。
- **工程目标：** 工程配置指向该型号，但实物尚未确认。
- **实物已确认：** 芯片丝印/装配记录等证据支持。
- **待核实：** 证据不足。
- **存在冲突：** 不同文件或实物信息不一致。

不要只写“芯片是 STM32G4”这类不足以支持外设和引脚判断的结论。
