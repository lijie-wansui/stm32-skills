# CubeMX 生成代码编辑规则（固件实现视角）

## 目标

本文件规定 `stm32-firmware` 如何在不破坏 CubeMX
生成配置的前提下接入项目代码。核心原则是：

**`.ioc` 和 CubeMX 生成配置只读；生成文件中仅明确标记的
`USER CODE BEGIN/END`
区域允许写入必要的项目接入代码；业务逻辑放在用户维护的
`App/`、`Control/` 文件中。**

## 1. 文件和区域的权限

| 对象                                               | 默认权限     | 固件 Skill 的处理方式            |
|----------------------------------------------------|--------------|----------------------------------|
| `Project.ioc`                                      | 只读         | 读取配置，不编辑                 |
| `MX_*_Init()` 中生成的初始化代码                   | 只读         | 读取和核对，不改写               |
| `HAL_*_MspInit()` 中生成的 GPIO/时钟/DMA/NVIC 配置 | 只读         | 读取和核对，不改写               |
| `stm32xx_it.c` 中生成的 IRQ Handler                | 只读         | 保留向量入口和 HAL IRQ 分发      |
| 成对 `USER CODE BEGIN/END` 标记之间                | 有条件可写   | 仅添加必要的项目接入代码         |
| `App/`、`Control/` 用户维护文件                    | 可按任务修改 | 放置实际业务实现                 |
| HAL、CMSIS、启动文件和厂商库                       | 禁止修改     | 使用 HAL API、回调或用户封装扩展 |

文件名称和用户区域因 MCU、CubeMX
版本及工程模板而异，必须先检查当前文件中的真实标记，不能凭经验假设。

## 2. 什么情况下允许写入 USER CODE 区域

允许的典型用途：

- 在 `USER CODE BEGIN Includes` 中包含项目头文件。
- 在外设初始化完成后的用户区域调用 `Control_Init()`
  或对应模块初始化函数。
- 在主循环用户区域调用 `Control_Run()` 或其他非中断任务。
- 在必要的用户区域添加简短的项目级变量声明或函数调用。

不允许：

- 修改、删除、移动或重命名 `USER CODE BEGIN/END` 标记。
- 修改标记区域之外的生成代码。
- 在用户区域内覆盖 `MX_*_Init()` 已生成的
  GPIO、RCC、TIM、ADC、DMA、NVIC、SPI/CAN 等配置。
- 把完整算法、状态机、通信协议或大段业务代码堆进 `main.c`。
- 在 `stm32xx_it.c` 中重写生成的 IRQ Handler 或删除 HAL IRQ 分发调用。
- 为了让代码编译而手工修改 HAL/CMSIS 或厂商库文件。

`USER CODE` 标记是用户代码保留区，不代表该区域可以任意改变底层硬件配置。

## 3. 推荐的接入方式

先查看当前
`main.c`，确认标记存在且位置符合预期。常见接入形态如下，标记名称必须以当前生成文件为准：

``` c
/* USER CODE BEGIN Includes */
#include "control.h"
/* USER CODE END Includes */

/* 外设初始化由 CubeMX 生成，保持不变。 */

/* USER CODE BEGIN 2 */
Control_Init();
/* USER CODE END 2 */

while (1)
{
    /* USER CODE BEGIN WHILE */
    Control_Run();
    /* USER CODE END WHILE */
}
```

`Control_Init()`、`Control_Run()` 的实现放在
`Control/control.c`；可复用算法和外设功能放在
`App/`。上例只展示接入关系，不规定所有项目都必须使用同名函数或主循环轮询。

HAL 用户回调优先定义在 `App/` 或 `Control/` 的用户维护 `.c`
文件中，并核对当前 HAL
的回调名称、参数和弱函数机制。不要为了定义回调而改写生成的 IRQ Handler。

## 4. 如果没有合适的 USER CODE 区域

1.  不自行在生成文件中插入或重排 `USER CODE` 标记。
2.  先把功能实现放入 `App/` 或 `Control/` 用户维护文件。
3.  查找当前工程已有的合法接入点。
4.  若没有接入点，向用户说明需要在哪个现有用户代码区域增加哪一行调用，等待用户确认或在其授权范围内接入。
5.  不通过改写 `MX_*_Init()`、MSP 或 IRQ Handler
    来绕过缺少接入点的问题。

## 5. 如果功能确实需要改变外设配置

- 先确认这是否属于 CubeMX 可配置项目。
- 如果可以配置，向用户提供 CubeMX
  页面、字段、当前值、建议值和原因；由用户手动修改并生成。
- 如果是 CubeMX 无法表达的特殊运行期配置，先说明为什么不能通过 CubeMX
  或普通 HAL API 完成，列出对时序和安全的影响。
- 需要在初始化后执行的项目专属配置，应由用户明确批准后放在独立的 `App/`
  或 `Control/`
  函数中，并在调用顺序中清晰标注；不得偷偷修改生成的初始化语句。
- 修改生成区之外的内容属于例外补丁，必须得到用户对具体文件和改动的明确批准，并记录重新生成可能覆盖该补丁的风险。
- HAL/CMSIS、启动文件和厂商库文件不在该例外范围内。

## 6. CubeMX 重新生成代码

Agent 默认不启动 CubeMX 代码生成，由用户手动操作。用户重新生成后：

1.  检查 `.ioc` 保存的配置。
2.  对照重新生成前后的文件差异。
3.  确认 `USER CODE` 区域中的用户接入代码仍然存在。
4.  确认生成的初始化参数、GPIO、时钟、DMA、NVIC 和触发配置符合 `.ioc`。
5.  检查是否产生重复初始化、重复回调、重复定义或用户代码丢失。
6.  再进行编译验证；编译通过仍不代表硬件验证通过。

## 7. 修改前后检查清单

- [ ] 已检查工作区原有未提交改动，没有覆盖用户工作。
- [ ] 已确认目标文件是否由 CubeMX 生成。
- [ ] 已确认 `USER CODE BEGIN/END` 标记成对且真实存在。
- [ ] `.ioc` 未被修改。
- [ ] 生成区只读，所有生成文件改动都位于允许的用户代码区域（若有）。
- [ ] 用户区域只包含必要的 include、变量声明或函数调用。
- [ ] 业务实现位于 `App/` 或 `Control/`。
- [ ] IRQ Handler 和 HAL 分发调用保持原样。
- [ ] HAL/CMSIS、启动文件和厂商库未修改。
- [ ] 修改后已检查完整 diff；若重新生成，已核对生成前后差异。

## 完成标准

交付时明确列出修改了哪些用户代码区域、哪些 App/Control
文件发生变化，以及 `.ioc`
和生成配置保持未修改。若没有合适的用户代码接入位置，应先向用户说明，不得自行突破生成代码保护边界。
