# 代码审查、验证与交付

## 修改前

1. 阅读当前项目 `AGENTS.md`、README 和相关模块源文件。
2. 检查工作区是否有用户未提交的修改；不得覆盖或丢弃。
3. 确认完整 MCU 型号、HAL 版本、外设初始化来源和构建方式。
4. 找到函数调用链、句柄定义、IRQ Handler、回调和 DMA 启动位置。
5. 明确本次任务涉及的文件、预期行为和不在本次修改范围内的内容。

## 修改中

- 优先最小范围修改。
- 不重构无关模块。
- 不改变现有工程架构，除非用户明确要求。
- 不擅自修改 `.ioc`、CubeMX 生成代码、引脚、时钟、DMA、中断优先级或外设参数。
- 不删除已有功能，不引入没有必要的第三方库。
- 新增源文件后，确认它确实加入当前工程的编译目标。
- 如必须修改生成文件，先解释为什么不能通过 App/Control 层实现，并取得用户明确授权。

## 修改后源码检查

### 结构和接口
- 文件位置符合 `App/Control/Core/main.c` 职责。
- 头文件声明与源文件定义一致。
- include guard、依赖和链接关系正确。
- 没有重复全局定义、重复回调或缺少源文件引用。
- App 不反向依赖 Control。

### HAL 与硬件接口
- HAL API、结构体、宏和回调来自当前工程版本。
- 参数单位、超时单位和句柄来源正确。
- DMA、中断和外设初始化调用关系完整。
- 不存在未经授权的引脚、时钟、PWM 或保护逻辑变更。

### 数据与实时性
- 数组、队列、帧和缓冲区长度正确。
- 异步缓冲区生命周期足够。
- ISR 与主循环共享数据的并发关系明确。
- 错误路径和恢复行为对应真实风险。
- 关键控制计算的执行上下文和时间要求合理。

## 编译验证

- 使用当前工程实际构建工具和构建配置。
- 记录实际执行的构建命令或 IDE 构建结果。
- 检查错误、警告和链接结果。
- 不通过删除功能或关闭告警来掩盖根因。
- 不使用陈旧 ELF/HEX/BIN 作为本次构建成功的证据。
- 无法构建时，说明缺少的工具、依赖或环境条件，并标注未验证范围。

## 硬件验证边界

严格区分：
1. 代码已编写。
2. 静态检查已完成。
3. 编译通过。
4. 已烧录到指定硬件。
5. 已完成串口、CAN、PWM、ADC、DMA 或中断等功能测试。
6. 已完成系统级硬件验证。

没有实际硬件或测量证据时，不得声称功能已经通过硬件验证。

对于功率电子项目，尤其不得把“编译通过”或“程序能启动”表述为“功率级可以安全运行”。PWM 输出、门极使能、故障清除和保护响应必须由用户按既定硬件安全流程验证。

## 修改汇报

较完整的修改完成后，简要说明：
- 修改了哪些文件。
- 每个文件承担什么职责。
- 新增或改变了哪些接口和调用关系。
- 编译结果及警告情况。
- 已完成哪些验证。
- 哪些行为仍需要用户烧录或进行硬件测试。

不要用“已完成”模糊覆盖未编译、未烧录或未测试的情况。
