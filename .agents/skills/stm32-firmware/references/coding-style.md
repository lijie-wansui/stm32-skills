# C 代码风格与实现原则

## 总体要求

- 代码首先要正确、清晰、容易理解和维护。
- 优先直接、简单的实现，不为追求抽象而增加复杂架构。
- 保持当前工程已有的命名和格式习惯；新代码在不冲突时遵循本页。
- 关键算法、外设行为、时序和数据格式使用充分的中文注释。
- 不机械地为每个变量、每行代码或显而易见的语句添加注释。

## 文件与接口

- 一个独立功能通常对应一组 `.c/.h` 文件。
- 头文件使用 include guard。
- 头文件只暴露调用方需要的类型、宏和函数声明。
- 文件内部变量和辅助函数尽量使用 `static`。
- 初始化函数与运行/计算函数分开。
- 不把大量无关功能堆进一个源文件。
- 不为只出现一次的简单语句机械拆分大量小函数。
- 不重复封装 HAL 已提供且没有必要再封装的功能。

## 命名

- 函数名称体现模块和动作，例如 `SOGI_Init()`、`CAN_App_Send()`、`Control_Init()`。
- 变量名称表达实际物理量或业务含义。
- 时间、电压、电流、频率等量尽可能体现单位，例如 `sample_time_s`、`current_A`、`frequency_Hz`。
- 宏使用清晰的大写名称。
- 结构体、枚举和函数前缀保持模块一致。
- 不为统一风格而对已有工程进行大规模无关改名。

## 中文注释应解释什么

重点解释：
- 模块用途和接口职责。
- 关键参数含义、单位和合法范围。
- 算法公式对应的物理意义或计算步骤。
- 中断与 DMA 的触发关系。
- 数据帧格式、字节序和缓冲区布局。
- 不直观的寄存器操作及其原因。
- 特殊时序要求、硬件限制和状态转换条件。

注释应优先回答“为什么这样做”和“使用时要注意什么”，而不是逐字翻译代码。

## 参数与状态管理

- 可调参数集中定义，或通过初始化参数/结构体明确传入。
- 不在多个函数中重复散落同一个参数。
- 算法历史状态放入对应结构体。
- 不随意使用大量全局变量。
- 只有确实需要跨模块共享的变量才对外声明。
- 对固定硬件事实，优先与当前工程配置和原理图保持一致，不在多个源文件中重复硬编码。

## 不进行无意义的防御性编程

避免：
- 对生命周期明确且内部保证有效的对象反复做空指针检查。
- 对不可能发生的内部状态重复检查。
- 为简单功能增加没有设计依据的多层错误码、重试和超时状态机。
- 每个函数都机械添加参数检查和错误处理。
- 为了“通用”而引入配置管理器、驱动注册框架、消息总线或多层抽象。

但真实风险必须处理：
- 外部通信帧的长度、ID、格式和数据有效范围。
- 数组、队列和 DMA 缓冲区的边界。
- DMA/中断与主循环并发访问的数据。
- 可能造成错误功率输出或硬件损坏的故障条件。
- HAL API 确实可能返回且上层必须处理的状态。
- 算法明确要求的输入范围和数值约束。

判断标准：检查必须对应真实风险、接口约束或安全要求，而不是机械添加。

## 物理量和算法

- 公式、变量和代码的量纲保持一致。
- 明确采样周期、计数单位、频率单位、角频率单位及时间单位。
- 浮点和定点转换必须明确缩放系数、范围和溢出条件。
- 算法的候选状态、输入数据和内部历史状态应有清楚的接口。
- 不将某个项目的控制时序和硬件参数写入可复用算法模块，除非它们确实属于算法参数。

## 功率电子项目的额外约束

- 不擅自改变 PWM 频率、死区、互补输出、刹车输入、输出使能或故障清除逻辑。
- 不把“代码可运行”当作“功率级可以安全上电”。
- 上电默认状态、门极驱动使能和故障恢复必须遵循当前硬件设计和项目控制流程。
- 涉及电流/电压采样时，核对采样触发点、数据更新时间和控制算法使用时刻，不自行假定同步关系。
