# 外设应用模块设计

本页定义外设底层初始化与应用功能模块之间的边界。具体实现按当前 MCU、HAL 版本、原理图和实际需求调整，不强制所有项目使用相同驱动代码。

## CubeMX 文件与 App 文件分开

以 CAN 为例：

```text
Core/
├── Inc/
│   └── can.h
└── Src/
    └── can.c

App/
├── Inc/
│   └── can_app.h
└── Src/
    └── can_app.c

Control/
├── Inc/
│   └── control.h
└── Src/
    └── control.c
```

| 文件 | 责任 |
| --- | --- |
| `Core/Src/can.c` | CubeMX 生成的 CAN 外设初始化 |
| `Core/Inc/can.h` | 生成的外设句柄和相关声明 |
| `App/Src/can_app.c` | 用户维护的 CAN 应用功能 |
| `App/Inc/can_app.h` | CAN 应用功能对外接口 |
| `Control/Src/control.c` | 当前项目的通信策略、报文业务和控制动作 |

`can_app.c/.h` 不是 CubeMX 生成文件。它可以使用已经初始化的外设句柄和 HAL API，但不应无故重复初始化同一外设。

## App 外设模块适合承担什么

按项目需要选择，不要求每个模块都实现所有能力：
- 基础发送和接收接口。
- 标准帧/扩展帧或协议帧的组装与解析。
- 接收缓存或队列。
- 统一的数据打包与解析。
- 通用错误状态和必要的统计信息。
- 对上层暴露简洁的初始化、发送、取数据或状态读取接口。

模块不应替项目决定业务含义。例如 CAN 模块可以解析出 ID 和 payload，但收到某个 ID 后是否触发功率降额、故障停机或单元协同，应由 `Control/` 决定。

## 参考案例：can_app.c/.h

用户已有的 `can_app.c/.h` 可作为 App 外设应用模块的组织参考。当前已知的案例职责包括：
- 标准帧和扩展帧收发。
- 接收 FIFO 回调入口。
- 接收环形队列缓存。
- 主循环或上层调用的取帧接口。
- `int16`、`int32`、`float` 等数据打包和解析。
- 采样数组的打包与解析。

这些是参考案例的功能范围，不意味着每个新 CAN 模块都必须照搬。修改实际文件前必须读取当前版本的完整源码和头文件，确认函数名称、结构体、队列容量、帧格式和错误处理，不得凭本页重建不存在的接口。

### 该案例应遵守的边界

- `can_app.c` 管理通用收发和数据格式。
- `control.c` 决定何时发送、发送什么业务数据、接收报文后执行什么控制动作。
- 接收回调中只完成必要的取帧、缓存或事件提交；不在 ISR 中执行复杂控制算法或阻塞操作。
- 环形队列要明确 ISR 生产者和主循环消费者的所有权、读写索引更新方式及队列满时的处理。`volatile` 本身不能替代并发设计。
- 字节序必须写进协议约定。`float` 的传输还要确认双方对浮点格式、宽度和字节序的约定，不能只依赖 MCU 的默认内存布局。

### bxCAN 与 FDCAN 不可直接混用

用户常见工程中，STM32F103、STM32F407 与 STM32G474 涉及的 CAN 外设类型可能不同；应按完整型号和 Reference Manual 确认。

如果当前工程使用 bxCAN：
- 以当前工程 `HAL_CAN` 头文件、源文件和 CubeMX 生成代码为准。
- 核对过滤器、FIFO、通知使能和接收回调。

如果当前工程使用 FDCAN：
- 以当前工程 `HAL_FDCAN` 头文件、源文件和生成代码为准。
- 核对 Message RAM、过滤器、Rx FIFO、元素配置、通知和回调。
- 不将 bxCAN 的句柄、过滤器结构和 API 直接复制到 FDCAN。

不要仅因为模块文件名都叫 `can_app.c` 就认为底层实现可以跨系列原样复用。

## 其他外设应用模块

同样的职责划分适用于 KEY、SPI、UART、ADC 等：
- App 提供可复用的扫描、收发、缓存、转换或计算能力。
- Control 决定何时调用以及数据如何参与当前项目控制。
- CubeMX 负责生成的外设初始化仍由开发者在 `.ioc` 中维护。

如果一个模块只服务当前项目且无法合理复用，也可以放在 `Control/`，不必为了目录完整而强行抽象到 `App/`。
