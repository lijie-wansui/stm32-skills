# HAL API、芯片手册与版本核实

本页用于防止跨系列复制错误 API。F103、F407、G474 等工程都必须以当前工程实际使用的驱动和完整芯片型号为准。

## 先确认芯片与工程版本

从当前工程检查：
- `.ioc` 中选择的完整 MCU 型号。
- `stm32xxxx.h`、`stm32xxxxxx.h` 等设备头文件和编译宏。
- CMSIS Device 文件及启动文件。
- `Drivers/STM32xx_HAL_Driver/` 或当前 Pack 中的 HAL 目录。
- `stm32xx_hal_conf.h` 中启用的模块宏。
- CubeMX 生成的外设初始化文件和句柄声明。
- 编译器、构建配置和链接脚本。

不能只根据工程文件夹名称或用户口头提到的系列判断完整型号。若工程的 `.ioc`、设备头文件和启动文件互相矛盾，先报告冲突。

## API 核实的证据顺序

1. 当前工程实际包含的 HAL 头文件：确认函数声明、参数类型、句柄类型、宏和回调签名。
2. 当前工程实际使用的 HAL 源文件：确认函数行为、弱回调、注册回调机制、条件编译和状态变化。
3. CubeMX 生成的初始化代码：确认句柄实例、外设参数、DMA 绑定和 NVIC 设置。
4. 当前 MCU 的 Reference Manual：确认外设硬件机制、触发源、寄存器行为和限制。
5. Datasheet：确认具体型号的外设实例、引脚复用、电气特性和封装。
6. Errata：确认芯片已知问题。
7. ST 官方对应版本的 HAL/Cube 文档：作为补充，不得用另一个系列或另一个版本的在线文档替代本地工程实际代码。

如本地缺少关键资料，说明缺少的文件和需要核实的具体问题，再提供对应完整型号的 ST 官方资料入口或请用户提供资料。不要编造页码、函数签名或寄存器行为。

## 每次使用 HAL API 前核对

至少核对与当前操作相关的项目：
- API 函数名称、参数类型、返回类型和调用顺序。
- Handle 类型及其来源，是否已由 CubeMX 初始化。
- 参数单位：字节、数据项、转换数、帧数、tick、毫秒等。
- 超时语义和当前 HAL tick 是否可用。
- 相关模块配置宏是否启用。
- IRQ Handler 是否存在且调用正确的 HAL IRQ Handler。
- HAL 回调的名称、参数和运行上下文。
- 使用弱回调还是注册回调，是否有重复定义。
- DMA 请求映射、方向、数据宽度、模式和中断。
- API 的启动、完成、停止和错误恢复生命周期。

特别注意：不同外设 API 的长度参数不一定使用相同单位。不能将 UART 字节数、ADC 转换数量、SPI 帧数量等一概而论。

## F1 / F4 / G4 的差异

本 Skill 的重点适用对象是传统 STM32CubeMX 工程。不同系列通常使用各自的 HAL 驱动和设备头文件，但具体版本仍以当前工程为准。

常见差异包括：
- F1、F4、G4 的外设实例、引脚复用、时钟树和 DMA 架构可能不同。
- DMA 可能采用不同的通道/Stream/请求映射机制。
- 某些系列使用 bxCAN，另一些型号使用 FDCAN；对应初始化结构、过滤器、FIFO、中断和 HAL API 不能直接互换。
- 定时器高级功能、ADC 触发源、采样时间和校准机制可能存在差异。
- HAL 驱动版本之间也可能存在 API、宏和回调差异。

例如，用户常见的 STM32F103、STM32F407 与 STM32G474 项目不能仅凭“都是 STM32”就复制外设驱动。需要按完整型号确认其外设实例和驱动接口。

## 不要混入 STM32C5 专用流程

除非当前项目确实是 STM32C5 且用户要求使用对应新工具链，否则：
- 不使用 CubeMX2 的 `cube mx` 工作流。
- 不把 `.ioc` 当作 `.ioc2`。
- 不把 HAL2 的 handle、函数和回调签名套入传统 HAL 工程。
- 不把 C5 专用 Pack 路径、配置方式或示例代码当成 F1/F4/G4 的通用做法。

## 无法核实 API 时

不要猜。应明确告诉用户：
- 当前缺少哪个头文件、源文件、芯片手册或 HAL 版本信息。
- 哪个函数/回调/参数尚无法确认。
- 需要用户提供什么文件，或需要在工程中搜索什么内容。
- 在确认之前，不提交基于猜测的外设代码。
