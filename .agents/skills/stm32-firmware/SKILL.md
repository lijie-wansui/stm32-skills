# STM32 固件开发

根据本次任务选择相关参考章节，不把全部参考资料当作逐条执行的清单。先理解现有工程，再进行最小范围修改；不得为了套用模板而重构正常工作的项目。

## 适用范围

用于：

- 新建或修改 STM32 C 固件源文件。
- 设计和维护 `App/` 可复用功能模块。
- 设计和维护 `Control/` 项目控制逻辑。
- 整理 `main.c`、HAL 外设调用、中断回调和 DMA 数据处理。
- 审查已有固件代码、模块边界和接口。

不负责：

- 代替开发者操作 CubeMX 修改
  `.ioc`、外设参数或重新生成工程。默认由开发者手动配置，助手只读取和审核。
- 修改 CubeMX 生成代码中 `USER CODE BEGIN/END`
  区域之外的内容；这些区域默认受保护。
- 环境安装、工具链配置、独立构建/烧录流程和系统级故障调试。这些任务应按对应的专用
  Skill 处理；当前 Skill
  只在固件修改中进行必要的源码检查和可用的编译验证。

## 与其他 Skill 的分工

- 工程根目录、完整 MCU 型号、HAL/工具链版本不明确时，先使用
  `stm32-project` 核对。
- 需要分析 CubeMX 参数、定时器/ADC
  触发路由、PWM/采样相位或板级信号链时，使用 `stm32-peripheral`。
- 本 Skill 聚焦 C 代码实现、模块接口、HAL 调用、中断回调、DMA
  缓冲区和源码审查；不代替外设硬件机制分析。

## 工作流程

1.  **识别工程。** 阅读项目
    `AGENTS.md`、README、目录结构、`.ioc`、启动文件、设备头文件、HAL
    驱动目录和构建配置。确认完整 MCU 型号、实际 HAL
    版本、编译器及现有代码组织。型号或版本不明确时先查证，不凭目录名或记忆推断。
2.  **理解现有调用链。** 找到外设初始化位置、句柄声明、IRQ Handler、HAL
    回调、DMA
    启动位置和模块调用关系。先读现有实现，不重复初始化已初始化的外设。
3.  **确定代码归属。** 遵循
    [工程分层](references/project-structure.md)：可复用功能放
    `App/`，当前项目控制流程放 `Control/`，CubeMX 生成的底层初始化保留在
    `Core/`，`main.c` 负责系统初始化和控制入口。
4.  **核实 API。** 遵循 [HAL API
    核实流程](references/hal-api-lookup.md)，以当前工程的头文件、源文件、配置宏和芯片资料为准。不得凭训练记忆猜测
    HAL 函数、回调签名、参数单位或外设能力。
5.  **实现最小改动。**
    只修改完成任务所需的文件。保持现有工程架构和命名习惯；不引入无需求的管理器、服务层、复杂适配框架或第三方库。若目标文件由
    CubeMX 生成，先按 [CubeMX
    生成代码编辑规则](references/cubemx-generated-code-editing.md)
    判断可写区域。
6.  **检查异步行为。** 涉及中断、回调或 DMA 时，按 [中断与
    DMA](references/interrupts-dma.md)
    检查调用上下文、缓冲区生命周期、重入、完成事件和错误路径。
7.  **验证并汇报。** 按
    [代码审查与交付](references/review-and-verification.md)
    检查接口、编译结果和未验证事项。严格区分代码已编写、编译通过、已烧录和硬件验证通过。

## 项目代码分层约定

| 位置       | 职责                                                           | 不应承担的职责                    |
|------------|----------------------------------------------------------------|-----------------------------------|
| `Core/`    | CubeMX 生成的系统、GPIO、TIM、ADC、CAN 等底层初始化和 IRQ 分发 | 堆积完整项目控制流程              |
| `App/`     | 可复用算法和功能模块，如 KEY、CAN 应用、SOGI、PID、FCS-MPC     | 依赖当前项目的控制流程            |
| `Control/` | 当前项目的控制策略、时序、模块调用、调试和测试逻辑             | 重新实现已经由 App 提供的通用功能 |
| `main.c`   | HAL/时钟/外设初始化，调用控制初始化，进入主循环                | 堆积全部算法、项目状态和业务逻辑  |

详细边界、文件组织和示例见 [工程分层](references/project-structure.md)。

## 关键约束

- 使用传统 STM32CubeMX `.ioc` 工程时，不得擅自改用 CubeMX2、`.ioc2`、C5
  HAL2 API 或对应命令。
- F103、F407、G474 等 MCU 的外设架构、HAL
  驱动版本、句柄、DMA、中断和回调细节可能不同。统一代码组织和风格，不强制统一底层实现。
- 不复制其他系列的外设初始化代码后假定可用。尤其要区分不同 CAN 外设及其
  HAL API。
- `.ioc` 和 CubeMX 生成的外设配置/初始化代码默认只读。不得擅自修改
  `.ioc`、`MX_*_Init()`、MSP、DMA、NVIC、GPIO、时钟和其他生成配置，也不得启动
  CubeMX 重新生成。
- 只有生成文件中成对的 `USER CODE BEGIN/END`
  区域允许写入必要的项目接入代码；不得改动标记本身或区域外生成内容。用户代码区域不是修改外设配置的后门。
- 优先把业务逻辑、HAL 回调和项目控制代码放在
  `App/`、`Control/`。通常只在 `main.c` 的用户代码区域添加头文件和
  `Control_Init()` / `Control_Run()` 调用。
- 不修改 `stm32xx_it.c` 中生成的 IRQ Handler
  分发逻辑；项目中断业务优先通过 `App/Control` 中经核实的 HAL 回调实现。
- HAL、CMSIS、启动文件和其他厂商库文件禁止修改。
- 不覆盖已有用户代码，不随意改变引脚、时钟、DMA、中断优先级、PWM
  输出或外设初始化顺序。
- 代码以简单、清晰、中文注释充分为原则；不机械添加空指针检查、重试、超时和多层错误码，但真实接口边界和硬件风险必须处理。
- 功率变换项目中，不得因为增加或修改固件代码而默认启动
  PWM、解除故障锁定或使能功率级。输出使能和故障恢复必须服从项目明确的安全流程与硬件保护设计。

## 完成标准

- 代码放置位置符合项目分层，接口和调用关系清楚。
- 使用的 HAL API、回调和参数单位已由当前工程资料核实。
- 没有无关重构、`.ioc` 或生成配置变更，也没有修改 `USER CODE`
  区域之外的生成内容。
- 真实的输入边界、缓冲区、异步生命周期和错误路径得到处理。
- 已说明修改文件、实现内容、编译结果、警告及尚需硬件验证的行为。
