# STM32 外设配置与实现

本 Skill 负责把 MCU 外设能力、CubeMX 配置、HAL 实现、控制时序和板级电路联系起来。重点不是罗列 CubeMX 参数，而是判断配置是否真正满足项目的功能、时序和硬件要求。

按任务加载 `references/` 中对应章节，不要每次把所有外设章节都读一遍。

## 适用任务

- 设计或审核 TIM/PWM、ADC、DMA、CAN、UART、SPI、I2C 等外设配置。
- 审核用户手动完成的 CubeMX 配置，并解释每项设置是否合适。
- 对照 `.ioc`、CubeMX 生成代码、HAL 驱动、芯片参考手册和原理图。
- 分析外设时钟、PWM 频率、死区、采样时刻、触发源、中断频率和 DMA 数据流。
- 设计多个定时器、ADC、DMA 和通信外设之间的硬件触发/同步关系。
- 判断外设运行所需的 HAL 启动、IRQ、DMA 事件和数据更新时间；具体 C 代码实现交给 `stm32-firmware`。
- 为电力电子控制系统分析 PWM、采样、控制中断、通信协同和硬件保护之间的关系。

## 不负责的任务

- 不负责完整工程识别和 MCU 资料库管理；需要时配合 `stm32-project`。
- 不负责通用 C 代码组织和整体固件架构；遵循 `stm32-firmware`。
- 不编写完整 C 驱动、应用模块或控制算法；代码实现交给 `stm32-firmware`。
- 不负责与外设无关的论文算法推导。
- 不代替用户操作 CubeMX。默认由用户手动配置，AI 读取 `.ioc` 和生成代码进行审核。
- 不擅自修改 `.ioc`、CubeMX 生成的初始化文件或重新生成工程。
- 不负责构建、烧录、示波器测量和硬件验证；只能明确提出验证方法和待验证项目。

## 工作原则

1. **先确认对象。** 确认完整 MCU 型号、封装、当前 HAL 版本、CubeMX 版本、外设实例和实际引脚。不得只凭 F1/F4/G4 系列简称推断功能。
2. **先确认需求。** 明确外设要完成的功能、输入输出信号、频率/速率、触发关系、实时期限和板级连接。不要先给一组通用参数。
3. **先看硬件，再看配置。** 对照原理图、BOM 和外部器件数据手册，确认信号极性、电平、隔离、终端、模拟前端、保护路径和引脚连接。
4. **用户配置，AI 审核。** 用户在 CubeMX 手动设置；AI 检查 `.ioc`、截图和生成代码，指出正确项、问题项及修改路径。没有明确授权，不直接改配置文件。
5. **按证据核实。** HAL 函数、回调签名、参数单位、DMA 请求映射、定时器触发源和寄存器行为，必须核对当前工程文件和对应芯片 Reference Manual。
6. **区分配置、启动和运行。** CubeMX 配置成功不等于外设已启动；初始化代码存在不等于信号已经输出；中断使能不等于回调已正确实现。
7. **先建立时序，再写代码。** 画清楚触发源、事件、IRQ/DMA、回调、控制逻辑和数据更新时间，再确定代码放置位置。
8. **最小实现。** 复用现有 HAL 句柄和初始化，不重复初始化外设；不引入无需求的驱动框架、管理器或多层封装。
9. **明确验证边界。** 代码审查、编译通过、外设启动、引脚波形正确和功率级安全运行是不同层次，不得混为一谈。

## 核心工作流程

1. 阅读项目 `AGENTS.md`、README 和当前工程资料；必要时按 `stm32-project` 的流程确认 MCU 与工程版本。
2. 明确外设任务：功能、信号、目标参数、实时性、启动/停止条件和异常行为。
3. 查看原理图、BOM、外部器件手册，确认 MCU 引脚和外部电路。
4. 查看 `.ioc` 中对应外设、GPIO、RCC、DMA、NVIC 和触发配置。
5. 查看 CubeMX 生成的初始化代码、句柄、IRQ Handler、HAL 回调及启动位置。
6. 查当前 HAL 头文件/源文件与对应 Reference Manual，核实 API、事件、触发和限制。
7. 先给出 CubeMX 配置审核结论；若需要修改，提供具体页面、字段、建议值和原因，由用户手动修改。
8. 若需要修改 C 代码，再转交 `stm32-firmware` 按项目分层实现；本 Skill 不代替固件代码实现。
9. 输出外设时序、配置结论、代码改动和待验证事项。

## 项目代码边界

分析外设与应用的接口时，遵循 `stm32-firmware` 中的项目分层：
- `Core/`：CubeMX 生成的外设初始化和 IRQ 底层分发。
- `App/`：可复用外设功能模块，例如 CAN 基础收发、UART 数据接收、KEY、SOGI 等。
- `Control/`：当前项目如何启动外设、何时采样、如何处理数据、何时更新 PWM，以及项目调试/测试/正式控制逻辑。
- `main.c`：系统初始化、外设初始化调用和控制入口。

不要求建立 `Test/` 目录。不要把某个项目的控制策略塞进通用 App 外设模块。具体文件修改和代码实现由 `stm32-firmware` 负责。

## 关键约束

- F103、F407、G474 的 DMA 架构、CAN 类型、定时器功能、ADC 触发和 HAL API 可能不同；逐工程核实，不复制系列间代码后假定可用。
- bxCAN 与 FDCAN 不可混用；F1/F4/G4 的具体支持情况必须按完整型号确认。
- 定时器时钟不能直接等同于 SYSCLK/HCLK；必须按 RCC 时钟树和具体系列规则核对。
- Center-aligned PWM 的更新事件、中断频率和重复计数器行为必须查对应 Reference Manual，不能假设每个 PWM 周期只进一次中断。
- DMA 完成事件不一定代表外设物理传输已经完全结束。
- `volatile` 不能替代 ISR/DMA 与主循环之间的并发设计。
- 不机械增加空指针检查、错误码、重试、超时和多层状态机；只处理真实存在的接口风险、并发风险和硬件安全风险。
- 不擅自改变 PWM 极性、死区、Break、MOE、门极驱动 RST/EN 或故障清除逻辑。
- 不建议通过屏蔽硬件保护、强制输出 PWM 或绕过故障链来“方便调试”。

## 完成标准

- 外设实例、引脚、时钟和硬件连接已确认或明确标记未知。
- CubeMX 配置、生成代码、HAL 实现和硬件信号链之间的关系已核对。
- 关键频率、触发时刻、IRQ/DMA 行为和参数单位有依据。
- HAL API 与回调来自当前工程版本，而不是凭记忆编造。
- 修改建议能定位到 CubeMX 页面/字段，且未擅自改动 `.ioc`。
- 代码实现遵循项目现有分层和最小改动原则。
- 报告明确区分配置审核、编译验证和实物验证。
