# CubeMX 外设配置审核流程

## 目标

用户手动操作 CubeMX，AI
负责只读检查配置、审核生成代码并解释修改方法。审核重点是配置是否满足项目需求，而不是追求
CubeMX 页面全部变成绿色。

本 Skill 不编辑 `.ioc`、CubeMX 生成文件或其中的 `USER CODE BEGIN/END`
区域。用户代码接入交给 `stm32-firmware`。

## 1. 审核前必须掌握的信息

至少确认：

- 完整 MCU 型号和封装。
- 当前 `.ioc` 对应的工程。
- CubeMX 版本（能从项目或用户信息确认时记录）。
- 当前工程 HAL/CMSIS 软件包版本。
- 外设实例及实际使用的 MCU 引脚。
- 外部器件和原理图连接。
- 用户期望的功能、频率/速率和触发时序。

信息不足时先说明缺少什么，不要直接给一组猜测配置。

## 2. 审核证据顺序

1.  `.ioc`：用户在 CubeMX 中表达的配置意图。
2.  CubeMX 生成代码：当前保存的初始化参数和 NVIC/DMA 初始化。
3.  当前工程实际构建配置：确认生成文件是否参与编译。
4.  当前 HAL 头文件/源文件：确认句柄、API、回调和参数单位。
5.  MCU Datasheet：确认引脚、封装、外设实例和电气特性。
6.  MCU Reference Manual：确认时钟、触发源、事件、DMA 请求和寄存器行为。
7.  原理图/BOM/外部器件手册：确认真实电路连接。
8.  Errata：检查相关外设是否存在芯片修订版限制。

不同证据不一致时，指出冲突，不擅自选一个当作正确结果。

## 3. 按页面检查

### Pinout & Configuration

- MCU 引脚是否属于目标封装实际引出引脚。
- 外设实例和通道是否支持所选引脚复用。
- GPIO Mode、Pull-up/Pull-down、Output Type 和 Speed 是否合理。
- 同一引脚是否发生复用冲突。
- 输入/输出极性是否与外部电路一致。
- 是否存在未分配但实际需要的 GPIO，例如驱动使能、故障输入、片选和复位。

### Clock Configuration

- HSE/HSI 等时钟源选择是否与硬件晶振/时钟输入相符。
- PLL 输入、倍频、分频和系统时钟是否满足芯片限制。
- AHB/APB 总线频率是否超出对应型号限制。
- 外设内核时钟来源是否正确。
- 定时器时钟是否按具体系列的 RCC 规则计算。
- ADC、FDCAN、USB
  等具有独立内核时钟选择的外设，是否选择了实际可用且满足指标的时钟源。

不要把 170 MHz、168 MHz 或其他常见频率当作所有工程的默认值。

### DMA Settings

- 该外设是否真的需要 DMA。
- DMA 请求是否属于当前 MCU 的正确实例/通道/Stream/DMAMUX 请求。
- Direction、Mode、Peripheral/Data Width、Memory/Data Width 是否匹配。
- Memory Increment 和 Peripheral Increment 是否合理。
- Priority 是否符合实时性需求。
- DMA 中断是否需要使能。
- 缓冲区大小和数据类型是否与代码一致。

DMA 具体映射和可选项随系列不同，必须查当前 MCU 的 Reference Manual 和
CubeMX 生成结果。

### NVIC Settings

- 是否需要中断；如果只用轮询或 DMA 完成中断，不要无理由开启外设中断。
- IRQ 是否使能。
- 抢占优先级和子优先级是否符合系统实时性设计。
- 是否存在多个中断优先级关系不合理或优先级反转风险。
- IRQ Handler 是否由生成代码正确调用 HAL 对应处理函数。
- HAL 回调是否确实存在且签名正确。

NVIC
优先级数值越小通常表示优先级越高，但优先级分组会影响抢占优先级和子优先级的位分配；必须查看当前工程设置。

## 4. 生成代码审核

根据外设查看对应 `MX_*_Init()`：

- 时钟使能。
- GPIO 复用和电气配置。
- 外设模式和时序参数。
- DMA 句柄关联。
- NVIC 优先级和使能。
- HAL 初始化函数及参数。
- 初始化顺序与依赖关系。

特别检查是否存在：

- `.ioc` 与生成代码不一致。
- 代码手工改动但 `.ioc` 没有同步。
- 生成文件未参与当前构建。
- 初始化函数存在但 main 没有调用。
- 初始化完成但没有启动外设。
- 中断使能了但 IRQ Handler 或回调缺失。
- DMA 配置了但没有启动 DMA 传输。
- 同一外设在多个位置重复初始化。

## 5. 审核结果应该怎么给用户

用户需要的是能照着操作的配置结论，不需要长篇罗列全部理论。

建议按顺序输出：

1.  总体结论：通过 / 部分需要修改 / 暂时无法判断。
2.  已经正确的配置：列出关键项即可。
3.  需要修改的配置：给出 CubeMX 页面、字段名称、建议值和原因。
4.  暂时不需要配置的项目：说明为什么可以留空。
5.  生成代码需要复核的内容。
6.  下一步用户需要提供的截图或文件。

如果用户只发截图：

- 仅对截图可见的字段下结论。
- 看不到的设置标记为未检查，不推断其值。
- 需要完整判断时，请用户补充 `.ioc` 或对应页面截图。

## 6. 修改权限：只读审核

本 Skill 对以下内容一律只读：

- `.ioc` 配置文件。
- CubeMX 生成的初始化代码、头文件、MSP 文件和 IRQ Handler。
- 生成文件中的 `USER CODE BEGIN/END` 用户代码区域。
- CubeMX 生成的工程配置文件。

需要改变引脚、时钟、外设模式、DMA、NVIC、触发源、PWM、ADC 或通信参数时：

1.  指出 CubeMX 页面、字段、当前值、建议值和原因。
2.  由用户在 CubeMX 中手动修改并保存。
3.  由用户执行代码生成。
4.  再次读取 `.ioc` 和生成代码，核对差异及初始化结果。

`USER CODE` 区域虽然允许固件开发任务写入项目代码，但不属于本 Skill
的编辑范围。需要增加 `Control_Init()`、`Control_Run()`
或回调实现时，交给 `stm32-firmware`，并遵守其生成代码保护规则。

详细的文件分类、可写区域、禁止修改内容和重新生成检查见 [CubeMX
生成代码保护规则](cubemx-generated-code-protection.md)。

## 7. 重新生成后的复核

用户重新生成代码后，重新检查：

- `.ioc` 中的配置是否与用户期望一致。
- 对应 `MX_*_Init()`、MSP、DMA 和 NVIC 初始化是否与 `.ioc` 一致。
- `USER CODE BEGIN/END` 区域中的项目接入代码是否保留。
- 是否出现意外的用户代码丢失、重复初始化或外设参数变化。
- 生成文件差异是否符合本次配置变更的预期。

不能仅凭 CubeMX 显示生成成功，就认定配置、代码和硬件行为正确。
